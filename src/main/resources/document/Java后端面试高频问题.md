## JVM 运行时数据区

分为五个区域：程序计数器、虚拟机栈、本地方法栈、堆、方法区（JDK 8 之后由元空间实现）。
其中**堆和方法区是线程共享**的，程序计数器、虚拟机栈、本地方法栈是**线程私有**的。

高频追问：`StackOverflowError` 一般是递归过深导致栈帧太多；`OutOfMemoryError: Java heap space`
是堆里对象回收不掉或一次加载太多数据；`OutOfMemoryError: Metaspace` 通常是动态生成类过多
（比如大量 CGLIB 代理）导致元空间撑满。

## 垃圾回收：怎么判断对象该回收

主流方案是**可达性分析**，从 GC Roots 出发做可达性遍历，不可达的对象才可能被回收。
不用引用计数法，因为它解决不了对象之间循环引用的问题。

常见的 GC Roots 有四类：虚拟机栈中局部变量引用的对象、方法区中静态变量引用的对象、
方法区中常量引用的对象、本地方法栈中 JNI 引用的对象。

分代收集思路：新生代对象朝生夕死，用**复制算法**（Eden + 两个 Survivor，默认比例 8:1:1），
代价是浪费一部分空间；老年代对象存活率高，用**标记-整理**或**标记-清除**。

## HashMap 为什么线程不安全

JDK 7 的头插法在并发扩容时可能形成环形链表，导致 `get` 死循环；JDK 8 改成尾插法解决了环的问题，
但并发 `put` 仍可能丢数据——两个线程同时判断槽位为空并写入，后写的会覆盖先写的。

想要线程安全用 `ConcurrentHashMap`：JDK 7 用分段锁（Segment），JDK 8 改成
**CAS + synchronized 锁单个桶**，锁粒度更细，并发度更高。

## 线程池的七个参数

核心线程数、最大线程数、空闲存活时间、时间单位、阻塞队列、线程工厂、拒绝策略。

执行顺序：先用核心线程 → 核心满了进队列 → 队列满了才开新线程直到最大线程数 → 再满就走拒绝策略。
**很多人记反**：不是"核心满了就开新线程"，而是先塞队列。

常见拒绝策略：`AbortPolicy`（默认，抛异常）、`CallerRunsPolicy`（调用者线程执行）、
`DiscardPolicy`（静默丢弃）、`DiscardOldestPolicy`（丢最老的）。

## MySQL 索引为什么用 B+ 树

B+ 树非叶子节点只存键不存数据，所以**单页能放更多键**，树更矮，磁盘 IO 次数更少；
叶子节点用链表串起来，范围查询和排序可以直接顺序扫描。

对比：B 树每个节点都存数据，同样页大小能放的键少；哈希索引只支持等值查询，不支持范围。

索引失效的常见场景：对索引列做函数运算、隐式类型转换、`like '%xxx'` 前导模糊、
联合索引不满足最左前缀、`or` 连接的条件有未建索引的列。

## 事务隔离级别与 MVCC

四种隔离级别：读未提交、读已提交（RC）、可重复读（RR，MySQL 默认）、串行化。
MySQL 的 RR 通过 **MVCC + 间隙锁**基本解决了幻读。

MVCC 的做法：每行记录有隐藏的 `trx_id` 和 `roll_pointer`，通过 undo log 构造版本链，
读的时候按 ReadView 判断哪个版本可见。RC 每次查询都生成新 ReadView，RR 只在第一次查询时生成。

## Redis 缓存三大问题

**穿透**：查不存在的数据，请求全打到数据库。解法：缓存空值（设短过期时间）、布隆过滤器。

**击穿**：某个热点 key 过期瞬间，大量请求同时打到数据库。解法：互斥锁重建、
逻辑过期（不设 TTL，异步更新）。

**雪崩**：大批 key 同时过期或 Redis 宕机。解法：过期时间加随机值、多级缓存、
Redis 高可用（哨兵 / 集群）、服务端限流降级。

## Spring 事务失效的场景

1. 方法不是 `public`（Spring AOP 代理限制）
2. 同类内部方法直接调用（走的是 `this`，没经过代理）
3. 异常被 `catch` 吞掉，没有抛出
4. 抛的是受检异常而 `rollbackFor` 没配（默认只回滚 `RuntimeException`）
5. 类没有被 Spring 管理（自己 `new` 出来的）
6. 数据库引擎不支持事务（比如 MyISAM）
